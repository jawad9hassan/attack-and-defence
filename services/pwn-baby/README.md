# pwn-baby: Stack Buffer Overflow (ret2win)

خدمة شبكية بسيطة مكتوبة بـ C، تسألك عن اسمك وتردّ عليك. فيها ثغرة
**stack buffer overflow** كلاسيكية، والهدف توصل لدالة `win()` الموجودة
في البرنامج لكن ما تُستدعى أبداً من المسار الطبيعي.

## تشغيلها

```bash
cd services/pwn-baby
docker compose up --build
```

الخدمة تستمع على المنفذ `9999`:

```bash
nc localhost 9999
```

## الكود (مو مخفي عنك، هذا هو التمرين: اقرأه وافهمه)

شوف `src/vuln.c`. لاحظ شيئين:

1. `win()` دالة موجودة وتطبع الفلاق، لكن `main()` ما يستدعيها أبداً.
2. `vulnerable_echo()` تستخدم `gets(name)` على مصفوفة ثابتة الحجم
   `char name[64]`. دالة `gets` **لا تتحقق من طول المدخل إطلاقاً**،
   فلو أدخلت نص أطول من 64 بايت، البيانات الزايدة تكتب فوق ذاكرة
   المكدس (stack) اللي بعد المصفوفة — بما فيها **عنوان الإرجاع
   المحفوظ** (saved return address)، أي وين البرنامج يرجع بعد ما
   تنتهي الدالة الحالية.

## الفكرة اللي تحتاج تكتشفها

إذا قدرت تحسب **بالضبط** كم بايت تحتاج قبل ما توصل لعنوان الإرجاع،
وبعدين تحط هناك **عنوان دالة `win()`** بدل عنوان الإرجاع الأصلي،
البرنامج بيقفز لـ `win()` بدل ما يرجع لـ `main()` بشكل طبيعي.

### خطوات التحليل المقترحة

1. **اعرف عنوان `win()`:**
   ```bash
   objdump -d src/vuln | grep -A2 "<win>:"
   ```
   بما إن البرنامج مبني بخيار `-no-pie`، عنوان `win()` **ثابت** ولا
   يتغير بين كل تشغيلة (هذا قصدي، عشان يسهل عليكم التمرين أول مرة).

2. **اعرف "طول الحشو" (offset) قبل عنوان الإرجاع:**
   هذا الجزء الأهم وتحتاج تكتشفه بنفسك. فكر: المصفوفة حجمها 64 بايت،
   لكن فوقها في المكدس فيه قيمة محفوظة ثانية (`saved RBP`) قبل ما تصل
   لعنوان الإرجاع. جرب ترسل أطوال مختلفة (مثلاً 64، 72، 80...) وراقب
   متى يتغير سلوك البرنامج (يطبع الفلاق، يتعطل، أو يرجع طبيعي). هذا
   أسلوب **binary search** بسيط، أو استخدم أداة `gdb` مع `pwndbg` إذا
   متوفرة عندك لمراقبة المكدس مباشرة.

3. **اكتب exploit بلغة بايثون** يبني الحمولة (payload):
   ```
   payload = b"A" * <طول_الحشو> + struct.pack("<Q", <عنوان_win>)
   ```
   ولاحظ: العنوان لازم يُحوّل لـ **little-endian** بـ 8 بايت
   (`struct.pack("<Q", addr)`)، لأن المعمارية `x86-64`.

4. **أرسل الحمولة عبر الشبكة** (مو عبر `stdin` مباشرة، لأن الخدمة
   تشتغل عن بعد في الحاوية). استخدم مكتبة `socket` في بايثون أو حتى
   `nc` مع إعادة توجيه:
   ```bash
   python3 -c "print('A'*72, end='')" | nc localhost 9999
   ```
   (هذا مثال تقريبي، لازم تضيف العنوان بالصيغة الصحيحة، ماهو نص عادي).

## أدوات تحتاجها

| الأداة | ليش |
|---|---|
| `objdump -d` | تشوف الكود المُجمّع وتلقى عنوان `win()` |
| `gdb` (+ `pwndbg` لو متوفر) | تشغّل البرنامج محلياً وتراقب المكدس أثناء التنفيذ |
| Python `struct` | تحول الأرقام لصيغة bytes بالترتيب الصحيح |
| Python `socket` | ترسل الحمولة عبر الشبكة للمنفذ 9999 |

**لا تطلب مني القيمة الجاهزة لـ offset.** جرب توصل لها بنفسك بالخطوات
أعلاه، وإذا علقت أكثر من 30-45 دقيقة ارجع لي وقول لي بالضبط وش جربت
ووش طلع (مثلاً: "جربت 64 بايت والبرنامج تعطل بـ Segmentation fault"،
أو "جربت 72 ومافيه تغيير")، وأعطيك تلميح أدق حسب وين بالضبط علقت.

## دور المدافع

بعد ما تحصل على الفلاق، فكر كيف تصلّح `vuln.c` بدون ما تغيّر سلوك
البرنامج الطبيعي (لازم يستمر يسأل عن الاسم ويرد عليك). فيه أكثر من
طريقة صحيحة:
- استبدال `gets()` بدالة تتحقق من الحجم (مثل `fgets`).
- تكبير المصفوفة مو حل كافي لحاله، لأنه بس يأخر المشكلة.
- إضافة خيارات تصريف (compiler flags) تفعّل حماية stack canary.

بعد التصليح، أعد البناء (`docker compose up --build`) وتأكد نفس
الحمولة اللي استخدمتها قبل الآن تفشل (البرنامج يتعطل بأمان أو يرفض
المدخل، بدون ما يوصل لـ `win()`).
