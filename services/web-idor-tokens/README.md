# Challenge: QuickNote (Web, ladder rung 6 of 10)

A "share your note with a link" feature. No login, no sequential
numeric id to increment like `web-idor` -- just a 16-character token in
the URL that looks exactly like a random secret. It isn't one.

## Running it

Standalone:

```bash
cd services/web-idor-tokens
docker compose up --build
```

Or as part of the full platform:

```bash
docker compose up --build web-idor-tokens   # from the repo root
```

Open `http://localhost:5005`.

## Attacker role

1. Open the homepage. It hands you alice's share link directly --
   `/n/<token>`. Load it, confirm it shows alice's note.
2. That token is 16 hex characters. If it were generated from real
   randomness (a CSPRNG, stored server-side), there would be nothing to
   do here. Start from the assumption that it isn't, and ask: what is
   the *smallest* amount of information that, if you had it, would let
   you compute this exact same token yourself?
3. Try computing a few well-known hash functions over alice's username
   (not her password, not her note -- just the string `alice`) and
   truncating to 16 characters. Compare against the token you were
   given.
4. Once you know the formula, the only remaining question is: what
   username does the admin account use? This is not meant to be hard --
   it's the single most predictable username in the challenge.

**Don't ask for the exact hash function or truncation length.** You
have the token for a known username (`alice`) and the matching note
content to confirm a guess against. That's a known-plaintext check you
can run against any formula you try.

## Defender role

Open `app/app.py` and look at `make_token`:

```python
def make_token(username: str) -> str:
    return hashlib.sha256(username.encode()).hexdigest()[:16]
```

The bug: this "unguessable-looking" token is a pure function of a
**public** value (the username) and nothing else -- no per-account
random salt generated at signup, no server-side secret key mixed into
the hash, no stored random token issued and looked up server-side. If
you can compute the inputs, you can compute the output, full stop.

The fix is to make the token actually derived from something an
attacker cannot already know or guess:

```python
import secrets
# generated ONCE at account-creation time and stored server-side,
# looked up by token -- never recomputed from the username again
token = secrets.token_hex(16)
```

or, if you want it to stay deterministic from the username (so it
doesn't need a lookup table), mix in a real per-deployment secret with
an HMAC instead of a bare hash:

```python
token = hmac.new(SERVER_SECRET_KEY, username.encode(), hashlib.sha256).hexdigest()[:16]
```

either of which an attacker cannot reproduce without the secret.

After patching, confirm:
- alice's own share link (generated by the new scheme) still opens her
  note
- `sha256("admin")[:16]` (or any other guess derived only from public
  information) no longer opens the admin's note

## Flag rotation

As part of the full platform, the admin note's content reflects
`/flag.txt`'s current value, rotated every round via `flagd` (see
`docs/ARCHITECTURE.md`). The token formula itself does not rotate --
only the flag you read through it changes.
